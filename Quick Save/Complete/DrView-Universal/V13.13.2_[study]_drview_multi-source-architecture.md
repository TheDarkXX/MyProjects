# 🏗️ Architectural Study: DrView Universal (Multi-Source Backend)

## 📌 Context (Compiled Truth)
The user requested an idea for converting DrView (currently a VS Code extension) into a Desktop and Web app that can sync from multiple sources like Logseq/Obsidian vaults, VPS, Firebase, and Cloud storage. 

Since the core renderer of DrView is already pure web technology (HTML/JS/CSS), it can easily be abstracted into a Universal UI. The challenge lies in data synchronization across different platforms.

### Decisions Made / Proposed Architecture: Adapter Pattern (Source Router)
Instead of hardcoding file system access (`vscode.workspace`), we introduce a **Source Router** with multiple **Adapters** implementing a unified interface. The UI will not care where the file comes from; it will only ask the Source Router for the file content.

```typescript
interface SourceAdapter {
  id: string              // "local-vault", "vps-brain", "firebase-notes"
  name: string            // Display name in UI
  icon: string            // Icon for the source
  
  // Core Operations
  list(path): FileEntry[]        
  read(path): string             
  write(path, content): void     
  watch(callback): void          // Real-time listener
  
  // Metadata
  capabilities: {
    writable: boolean
    watchable: boolean
    searchable: boolean
    offline: boolean
  }
}
```

#### Platform Implementations:
1. **Desktop App (Electron/Tauri):** Full access to `fs` (Local Vault), `ssh2` (VPS), Firebase SDK, and AWS SDK.
2. **Web App (Browser):** Local Vault requires `File System Access API` (needs explicit user permission), VPS requires a REST API proxy, Firebase works natively via SDK.
3. **VS Code Extension (Current):** Uses `vscode.workspace` API natively for local files.

### Strategic Recommendations:
- **Read-Only vs Read-Write:** A Read-Only system is exponentially simpler to build as an MVP since it avoids conflict resolution and lock files.
- **Federated vs Full Sync:** A Federated approach (where DrView simply reads from multiple isolated sources without forcing them to sync with each other) is highly recommended over a centralized "Full Sync" approach.
- **MVP Effort:** A Federated, Read-Only universal viewer could be built in 2-3 days using the existing renderer. A full-sync CRDT system (like Yjs) would take 3-4 weeks.
